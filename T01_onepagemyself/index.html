02 · DATA FLOW

프린트 토너 신청 과정을 데이터 구조로 연결했습니다

DB · 협업
상황

수작업으로 처리하던 프린트 토너 신청 과정을 자동화하는 팀 프로젝트를 진행했습니다.

행동

사용자의 토너 신청 정보를 기준으로 사용자·주문·제품·주문 상세 데이터를 구분하고, 테이블 간 관계와 필요한 컬럼을 SQL로 설계했습니다.

결과

토너 신청 과정에서 필요한 사용자·주문·제품 정보를 하나의 구조로 정리해, 팀이 각 기능에서 동일한 데이터 항목과 관계를 기준으로 작업할 수 있도록 했습니다.

이 경험이 보여주는 것

내가 맡은 부분만 보는 대신 사용자·서버·데이터베이스·화면이 어떻게 이어지는지 전체 흐름을 먼저 확인합니다.

데이터 구조와 설계 방식 사용자, 주문, 제품, 주문 상세 정보를 Users, Orders, Products, OrderItems 4개 테이블로 나누고, 각 테이블을 사용자·주문·제품 ID로 연결했습니다. Orders에는 주문 시각(order_date), 신청 수량(count), 프린트 유형(print_type), 토너 유형(toner_type)을 저장하고, Products에는 제품명·재고·색상을 관리하도록 구성했습니다.

공개 근거 실제 프로젝트의 create_table.sql을 바탕으로 개인정보와 테스트 계정 정보를 제외해 공개용 ERD로 정리했습니다.

공개용 ERD 보기

사용자 → 주문 → 주문 상세 → 제품으로 이어지는 테이블 관계와 주요 컬럼을 확인할 수 있습니다.

03 · TROUBLESHOOTING

Hyperledger Fabric 통신 오류를 로그부터 추적했습니다

분석 · 복구
상황

Ubuntu 환경에서 Docker 기반 Hyperledger Fabric 네트워크를 구축하던 중 Peer와 Orderer 간 통신 및 chaincode 작업 과정에서 TLS 관련 오류가 발생했습니다.

행동

Docker 컨테이너 상태와 Peer·Orderer 로그를 확인해 오류가 발생하는 구간을 좁혔습니다. 이후 TLS 인증서 경로와 설정값을 확인하고, tlsca 인증서 파일이 정상적으로 인식되는지 점검했습니다. 인증서 파일의 형식 문제를 정리한 뒤 네트워크를 다시 실행하며 통신 상태를 단계적으로 확인했습니다.

결과

TLS 인증서 관련 설정과 파일 문제를 수정한 후 Peer 통신을 정상화하고 chaincode 배포 및 거래 처리를 다시 진행할 수 있었습니다.

이 경험이 보여주는 것

설정값을 무작정 변경하기보다 컨테이너 상태와 로그를 먼저 확인하고, 인증서·경로·파일 형식처럼 통신에 영향을 주는 요소를 하나씩 확인하며 원인을 좁혀가는 방식으로 문제를 해결했습니다.

확인 가능한 구성 프로젝트에서 사용한 Hyperledger Fabric 네트워크의 핵심 구조를 개인정보와 민감한 인증서 정보 없이 공개용으로 정리했습니다. Python 스크립트에서 `peer chaincode invoke/query`를 실행해 Peer·Orderer와 통신하고, `SetMapping`/`GetMapping`으로 World State에 데이터를 저장·조회하는 흐름과 TLS 인증서 경로를 한눈에 볼 수 있습니다.

공개 근거 실제 프로젝트에서 사용한 Fabric 네트워크 구조와 chaincode 호출 흐름을 바탕으로 공개용 구성 근거를 제작했습니다. 개인 정보, 학교·팀 식별 정보, 인증서 원문과 비밀값은 포함하지 않았습니다.

Fabric 구성 근거 보기

실제 `submit_mapping.py`, `ascii_mapping_chaincode.go`, `compose-test-net.yaml`에 있는 호출 흐름과 TLS 설정만 공개용으로 정리한 자료입니다.
