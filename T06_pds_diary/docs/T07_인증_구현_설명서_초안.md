# T07 인증 구현 설명서 — 제출용 초안

> `[직접 확인 후 입력]`은 실제 배포 뒤 검증 결과로 교체합니다. 비밀번호·세션값·토큰·비밀키 원문은 적지 않습니다.

## ① 무엇으로 붙였나

인증은 **직접 구현 방식**을 선택했고, 암호 알고리즘 자체를 새로 만들지 않고 Cloudflare Workers 런타임의 표준 **Web Crypto API**를 사용했다. 비밀번호는 `PBKDF2-HMAC-SHA-256`으로 600,000회 반복하고 계정마다 16바이트 랜덤 salt를 만들어 `pbkdf2-sha256$반복수$salt$derivedKey` 형태로 D1에 저장한다.

로그인 상태는 JWT가 아니라 **opaque session**으로 관리한다. 로그인 시 32바이트 랜덤 세션값을 만든 뒤 브라우저에는 `HttpOnly + SameSite=Strict + HTTPS에서 Secure` 쿠키로 전달하고, D1에는 세션 원문이 아니라 SHA-256 해시만 저장한다. 세션 만료시간은 12시간이다.

외부 인증 서비스도 검토했지만 이번에는 고르지 않았다. T06의 Workers + D1 구조와 기존 자료를 그대로 이어 가면서 저장 비밀번호·세션 만료·로그아웃 후 거절·자료 소유권을 한 저장소에서 직접 설명하기에는 현재 방식이 더 단순했기 때문이다.

## ② 왜 그걸 골랐나

T06의 데이터 구조를 최대한 보존하는 것이 첫 번째 이유였다. 새 인증 서비스로 자료 저장 위치까지 바꾸기보다 기존 D1에 `users`, `sessions`와 `plans.user_id`만 추가하면 T06 데이터와 T07 인증을 한 흐름으로 설명할 수 있다.

또한 PBKDF2는 과제에서 허용한 되돌릴 수 없는 비밀번호 저장 방법 중 하나이고, Web Crypto API를 사용하면 PBKDF2 연산 자체를 직접 작성하지 않아도 된다. 세션도 서명 비밀키가 필요한 JWT 대신 서버 DB에서 폐기 가능한 불투명 세션을 사용해 로그아웃과 비밀번호 변경 시 이전 세션을 바로 끊을 수 있게 했다.

## ③ 어디를 어떻게 고쳤나

- `migrations/0002_auth.sql`: `users`, `sessions`, 5일 사용 기록 테이블을 추가하고 `plans.user_id`를 추가했다.
- `src/index.js`의 가입 흐름: 입력 검증 → PBKDF2 해시 → `users` 저장 → 첫 계정이면 T06의 `user_id IS NULL` 계획을 그 계정으로 승계 → 세션 발급 순서다.
- `src/index.js`의 로그인 흐름: 아이디 조회 → PBKDF2 검증 → 성공 시 랜덤 세션 발급 → `sessions`에는 세션 해시와 만료시각만 저장한다. 없는 아이디와 틀린 비밀번호는 같은 401 문구를 돌려준다.
- `src/index.js`의 로그아웃 흐름: 현재 세션 행을 D1에서 삭제하고 쿠키를 만료시킨다.
- `src/index.js`의 자료 조회 흐름: `plans.user_id = 로그인 사용자 ID` 조건을 서버 쿼리에 넣고, 할 일·실행기록·돌아보기는 소유한 계획과 JOIN하여 확인한다. 다른 사용자의 ID를 직접 요청하면 404로 처리한다.
- `public/index.html`, `public/app.js`: 로그인 전에는 로그인/가입 화면만 보이고 인증 성공 뒤에만 PLAN/DO/SEE/5일 기록 화면을 표시한다.
- `src/index.js`의 `/api/usage-study/*`: 실제 Asia/Seoul 오늘 날짜만 저장하고, 같은 날짜 중복을 막고, 2일차 뒤·3일차 앞 규칙 변경을 강제한다.

## ⑤ AI와 나

- AI에게 맡긴 일: T07 체크리스트를 T06 구조에 대응시키고, 인증/세션/소유권 분리/5일 기록의 구현 초안과 검증 절차를 만드는 일을 맡겼다.
- 내가 직접 판단한 일: 실제 첫 계정, 5일 동안 관찰할 질문·지표·계획 규칙, 2일차 뒤 바꿀 규칙, 그리고 배포 뒤 양방향 권한 검사의 실제 통과 여부는 내가 직접 정하고 확인한다.
- AI 말을 따르지 않은 일: 현재까지 과제 요구와 충돌해 버린 제안은 없었다. 대신 AI가 만든 결과를 그대로 통과로 간주하지 않고, 실제 배포 주소에서 요청/응답을 직접 재현한 결과만 제출 근거로 사용한다.

## ⑥ 아직 못 막은 것

**로그인 무차별 대입에 대한 rate limiting을 아직 붙이지 않았다.** 현재 틀린 로그인은 같은 문구로 응답하고 비밀번호는 느린 PBKDF2로 검증하지만, 동일한 사용자나 IP가 짧은 시간에 로그인 요청을 매우 많이 보내는 것을 별도로 제한하지는 않는다. 실제 서비스에서는 Cloudflare Rate Limiting/Turnstile 또는 서버 측 실패 횟수 제한을 추가해야 한다. 이 기능이 없으면 반복 비밀번호 추측과 불필요한 연산 부하 위험이 남는다.

추가로 비밀번호 재설정과 MFA도 구현하지 않았다.

1. 어디로 가나요: `[결과물 공개 URL]`을 새 시크릿 창에서 연다.

3. 무엇이 보이면 통과인가요: 로그인 뒤 내 자료만 보이고, 다른 계정 ID를 직접 요청하면 404, 로그아웃 뒤 같은 API는 401이 보이면 통과다.
4. 안 될 때는 무엇이 보이나요: 로그인하지 않았으면 `UNAUTHORIZED`, 남의 자료 ID면 `NOT_FOUND`, 같은 날짜 5일 기록을 중복 저장하면 `DUPLICATE_DATE`가 보인다.
