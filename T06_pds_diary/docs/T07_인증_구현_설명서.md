## ① 무엇으로 붙였나

인증은 **직접 구현 방식**을 선택했다. 외부 인증 서비스는 사용하지 않았고, 기존 T06의 Cloudflare Workers + D1 구조에 인증 기능을 추가했다. 비밀번호 파생 연산은 Cloudflare Workers 런타임의 표준 **Web Crypto API**를 이용해 `PBKDF2-HMAC-SHA-256`으로 처리한다.

비밀번호 저장 방식은 다음과 같다.

- 알고리즘: `PBKDF2-HMAC-SHA-256`
- 반복 횟수: `100,000`
- salt: 계정마다 16바이트 랜덤 값
- 저장 형식: `pbkdf2-sha256$100000$[salt]$[derivedKey]`
- 비밀번호 원문은 D1에 저장하지 않는다.

실제 D1에서 `aleph_diary`의 `password_hash`가 원문이 아닌 위 형식으로 저장된 것을 확인했다. 또한 같은 비밀번호로 만든 `test_a`, `test_b`의 저장값이 서로 달랐다.

로그인 상태는 JWT가 아니라 **서버 저장형 opaque session**으로 관리한다.

- 로그인 성공 시 32바이트 랜덤 세션값 생성
- 브라우저: `pds_session` 쿠키에 저장
- 쿠키 속성: `HttpOnly`, `SameSite=Strict`, `Secure`, `Max-Age=43200`
- 만료시간: 12시간
- D1 `sessions`에는 세션 원문이 아니라 SHA-256 해시와 만료시각만 저장
- 로그아웃 시 현재 세션 삭제
- 비밀번호 변경 시 해당 사용자의 기존 세션을 모두 삭제한 뒤 새 세션 발급

아이디는 **영문 소문자·숫자·점(`.`)·밑줄(`_`)·하이픈(`-`)만 4~40자** 허용한다. 초기에는 대문자를 서버에서 소문자로 바꾸는 방식이었지만, 입력값과 실제 저장값이 달라지는 것이 혼란을 줄 수 있다고 판단해 대문자를 처음부터 거절하도록 수정했다.

함께 검토한 다른 방법은 Auth0·Supabase Auth 같은 외부 인증 서비스였다. 인증 구현 부담은 줄어들지만, T06의 기존 Worker/D1 자료 승계와 소유권 검사를 한 저장소 안에서 설명하고 검증하기에는 현재 구조가 더 단순하다고 판단해 사용하지 않았다.

## ② 왜 그걸 골랐나

첫 번째 이유는 **T06 데이터와 구조를 최대한 그대로 이어가기 위해서**였다. 새 인증 서비스와 새 데이터 저장소를 추가하기보다 기존 D1에 `users`, `sessions`를 추가하고 기존 `plans`에 `user_id`를 연결하면 T06에 입력했던 계획·할 일·실행 기록·돌아보기를 그대로 T07에 이어 사용할 수 있다.

실제로 T07 첫 계정 `aleph_diary`를 생성했을 때 T06의 기존 계획 `T06 플랜두씨 다이어리 완성`이 해당 계정으로 승계되었고, 로그인 뒤 기존 계획·할 일·실행 기록이 그대로 보이는 것을 확인했다.

두 번째 이유는 **비밀번호 원문을 직접 보관하지 않기 위해서**였다. PBKDF2 연산 자체는 Web Crypto API에 맡기고 애플리케이션은 salt 생성·저장 형식·검증 흐름만 구성했다. 동일한 비밀번호를 사용한 두 테스트 계정의 저장값도 서로 다르게 생성되는 것을 D1에서 확인했다.

세 번째 이유는 **세션을 서버에서 즉시 끊을 수 있기 때문**이다. 서버 저장형 세션을 사용하면 로그아웃 시 현재 세션을 삭제하고, 비밀번호 변경 시 기존 세션을 모두 폐기할 수 있다. 실제로 `test_a`를 두 브라우저에서 로그인한 뒤 한쪽에서 비밀번호를 변경하자 다른 창의 기존 세션으로 `GET /api/plans`를 요청했을 때 `UNAUTHORIZED`로 거절됐다.

## ③ 어디를 어떻게 고쳤나

### DB 구조

`migrations/0002_auth.sql`에서 기존 T06 D1을 확장했다.

- `users` 추가
- `sessions` 추가
- 기존 `plans`에 `user_id` 추가
- `usage_study_config` 추가
- `usage_daily_records` 추가
- `plan_rule_changes` 추가

새 D1을 만들지 않고 기존 `t06-pds-diary-db`에 migration을 적용했다. 적용 뒤 기존 T06 데이터는 그대로 유지됐고, 첫 가입 전 기존 계획은 `user_id IS NULL` 상태였다. 첫 계정 생성 후 해당 계획이 `aleph_diary`에 연결됐다.

### 가입 흐름

`src/index.js`의 `register()` — 약 180줄부터

1. 아이디·비밀번호 입력값 검사
2. 같은 아이디가 이미 있는지 확인
3. PBKDF2 비밀번호 해시 생성
4. `users`에 계정 저장
5. 첫 계정이면 기존 `user_id IS NULL` T06 계획을 해당 계정으로 승계
6. 세션 생성 후 쿠키 발급

같은 아이디 `aleph_diary`로 다시 가입했을 때 `이미 사용 중인 아이디입니다.`로 거절되는 것도 확인했다.

### 로그인 흐름

`src/index.js`의 `login()` — 약 224줄부터

1. 아이디 조회
2. PBKDF2로 비밀번호 검증
3. 성공 시 세션 생성
4. D1에는 세션 해시와 만료시각 저장
5. 응답에는 사용자 정보와 만료시각만 반환

존재하는 아이디 + 틀린 비밀번호와 존재하지 않는 아이디 + 임의 비밀번호 모두 `아이디 또는 비밀번호를 확인해 주세요.`라는 같은 문구를 반환하도록 했다.

### 로그아웃·비밀번호 변경

- `logout()` — 약 256줄부터
- `changePassword()` — 약 263줄부터

로그아웃 시 현재 세션 행을 D1에서 삭제하고 브라우저 쿠키를 만료시킨다. 비밀번호 변경 시 새 비밀번호 해시를 저장하고 해당 사용자의 기존 세션을 모두 삭제한 뒤 새 세션만 다시 발급한다.

### 계정 삭제

`deleteAccount()` — 약 285줄부터

확인값 `DELETE`를 입력해야 삭제가 진행되며, 해당 사용자의 계획·수정이력·할 일·실행 기록·완료 기록·돌아보기·5일 기록·세션·계정까지 함께 삭제한다.

테스트 계정 `test_b`를 삭제한 뒤 D1에서 사용자·계획·할 일을 각각 조회했을 때 모두 0건인 것을 확인했다.

### 자료 소유권 검사

자료 격리는 화면에서 숨기는 방식이 아니라 **서버 쿼리에서 로그인 사용자 ID를 검사**하도록 만들었다.

- `ownedPlan()` — 약 390줄
  - `SELECT * FROM plans WHERE id = ? AND user_id = ?`
- `ownedTask()` — 약 394줄
  - `tasks`와 `plans`를 JOIN하고 `plans.user_id = ?` 검사
- `listPlans()` — 약 444줄
  - `WHERE p.user_id = ?`
- `getPlan()` — 약 456줄
  - 소유권 불일치 시 404
- `updateTask()` — 약 546줄
  - 수정 전에 `ownedTask()` 검사
- `deleteTask()` — 약 581줄
  - 삭제 전에 `ownedTask()` 검사
- `handleProtectedApi()` — 약 754줄
  - 세션에서 얻은 `auth.user_id`를 각 API에 전달
- `handleApi()` — 약 796줄
  - 인증되지 않은 보호 API 요청은 401

URL query, 요청 헤더, 요청 본문에 `user_id`나 다른 사용자 이름을 임의로 넣더라도 인증 근거로 사용하지 않는다. 서버가 신뢰하는 사용자 ID는 세션에서 확인한 `auth.user_id`뿐이다.

## ④ 안 열리는 것을 확인한 기록

아래 기록은 실제 배포 주소에서 직접 확인했다. 비밀번호·세션 원문은 기록하지 않았다.

### 확인 1 — 로그인 상태와 로그아웃 뒤 같은 요청

| 구분 | 요청 | 결과 |
|---|---|---|
| 성공 | 로그인 상태 `GET /api/plans` | `200 OK`, 내 계획 반환 |
| 거절 | 로그아웃 후 같은 `GET /api/plans` | `401 UNAUTHORIZED`, `로그인이 필요합니다.` |

주소와 요청 방식은 같고 달라진 것은 로그인 상태뿐이다.

### 확인 2 — 다른 계정 자료 읽기

테스트 자료:

- `test_a`: plan 2 `A 계정 보안 격리 검사`
- `test_b`: plan 3 `B 계정 보안 격리 검사`

| 구분 | 요청 | 결과 |
|---|---|---|
| 성공 | `test_a`가 자기 목록 `GET /api/plans` | `200`, A 계획만 반환 |
| 거절 | `test_a`가 `GET /api/plans/3` | `404 NOT_FOUND` |
| 거절 | `test_b`가 `GET /api/plans/2` | `404 NOT_FOUND` |

### 확인 3 — 다른 계정 자료 수정

테스트 할 일:

- `test_a`: task 8 `A 전용 자료 접근 차단 확인`
- `test_b`: task 9 `B 전용 자료 접근 차단 확인`

| 구분 | 요청 | 결과 |
|---|---|---|
| 성공 | `test_b`가 자기 task 9를 `PUT /api/tasks/9` | `200 OK` |
| 거절 | `test_a`가 `PUT /api/tasks/9` | `404 NOT_FOUND` |
| 거절 | `test_b`가 `PUT /api/tasks/8` | `404 NOT_FOUND` |

공격 뒤 D1에서 제목과 소유권을 다시 확인했을 때 A/B 자료가 각각 원래 계정에 그대로 남아 있었다.

### 확인 4 — 다른 계정 자료 삭제 및 삭제 전후 건수

| 구분 | 요청/확인 | 결과 |
|---|---|---|
| 성공 | `test_b` 계정의 `DELETE /api/auth/account` | 계정과 연결 자료 삭제 성공 |
| 거절 | `test_a`가 `DELETE /api/tasks/9` | `404 NOT_FOUND` |
| 거절 | `test_b`가 `DELETE /api/tasks/8` | `404 NOT_FOUND` |

양방향 공격 전후 자료 건수는 각각 `계획 1개 / 할 일 1개`로 동일했다. 이후 `test_b` 자체를 삭제한 뒤 D1에서 `users`, `plans`, `tasks`를 조회했을 때 `test_b`와 연결 자료가 모두 0건인 것을 확인했다.

### 확인 5 — URL·헤더·본문 위조와 목록 격리

`test_a` 로그인 상태에서 일부러 다음 정보를 보냈다.

```text
GET /api/plans?user_id=3&username=test_b
X-User-Id: 3
X-Username: test_b
```

결과는 `200`이었지만 목록에는 다음 한 건만 있었다.

```text
id = 2
title = A 계정 보안 격리 검사
user_id = 2
```

`test_b`의 plan 3은 반환되지 않았다.

또 `test_a`가 자기 task 8 수정 본문에 `user_id: 3`, `username: test_b`를 넣어도 task 8의 실제 소유자는 `test_a`로 그대로 유지됐다. 즉 URL·헤더·본문의 사용자 정보를 믿지 않고 로그인 세션의 사용자 ID만 사용한다.

### 비밀번호·세션 관련 추가 확인

- D1의 `aleph_diary.password_hash`는 비밀번호 원문이 아니라 `pbkdf2-sha256$100000$...` 형식이다.
- 같은 비밀번호를 사용한 `test_a`, `test_b`의 저장값은 서로 달랐다.
- 로그인 응답에는 `password`, `password_hash`, 세션 원문이 반환되지 않았다.
- 세션 쿠키는 `HttpOnly`, `SameSite=Strict`, `Secure`, `Max-Age=43200`으로 설정됐다.
- Request URL은 `/api/auth/login`이며 비밀번호나 세션값이 URL에 들어가지 않았다.
- 비밀번호 변경 뒤 다른 브라우저에 남아 있던 이전 세션은 `/api/plans` 요청에서 `UNAUTHORIZED`로 거절됐다.

제출물에 세션 쿠키를 적어야 할 때는 실제 값을 쓰지 않고 다음처럼 가린다.

```text
pds_session=[가림]; HttpOnly; SameSite=Strict; Max-Age=43200; Secure
```

## ⑤ AI와 나

### AI에게 맡긴 일

T07 체크리스트를 T06 구조에 대응시키고 인증·세션·사용자별 소유권 분리·5일 기록 기능의 구현 초안과 테스트 절차를 정리하는 데 AI를 사용했다. 문제가 발생했을 때 원인 후보와 수정 방향, 확인할 API 요청과 D1 SQL을 만드는 데도 활용했다.

### 내가 직접 판단한 일

T07을 새 저장소나 새 DB로 분리하지 않고 **최종 T06을 조상으로 가진 `T07-auth` 브랜치에서 기존 Worker와 D1을 그대로 고도화하는 방식**을 선택했다. 실제 사용할 본계정과 보안 검사용 테스트 계정을 분리했고, 5일 동안 관찰할 질문·지표·단위·계획 규칙도 직접 정했다.

통과 여부는 AI의 설명만으로 판단하지 않고 실제 배포된 Worker에서 직접 가입·로그인·로그아웃·API 호출·계정 전환·D1 조회를 수행해 확인했다.

### AI 말을 따르지 않은 일

초기에는 T07을 별도 폴더/프로젝트처럼 추가하는 방법이 제안됐지만, T07은 T06 고도화이고 기존 D1을 이어 써야 한다고 판단해 **같은 T06 프로젝트를 브랜치에서 직접 고도화하는 방식으로 변경**했다.

또 실제 사용 중 발견한 UI 상태 잔존, 대문자 아이디 자동 변환, UTC 시각 표시, 최초 규칙 표시 문제는 AI 초안을 그대로 두지 않고 직접 문제를 확인한 뒤 수정·재검증했다.

## ⑥ 아직 못 막은 것

### 1. 로그인 무차별 대입 rate limiting

같은 IP나 계정이 짧은 시간에 로그인 요청을 반복하는 것을 별도로 제한하지 않는다. 존재하지 않는 아이디와 틀린 비밀번호에는 같은 문구를 사용하고 있지만, 많은 비밀번호를 반복해서 시도하는 공격 자체는 차단하지 못한다.

실제 서비스라면 계정/IP 단위 로그인 실패 횟수 제한, 일정 시간 잠금, Cloudflare의 요청 제한 기능 등을 추가할 필요가 있다.

### 2. 비밀번호 재설정

비밀번호를 잊었을 때 이메일 등의 방식으로 안전하게 재설정하는 기능은 구현하지 않았다. 따라서 사용자가 비밀번호를 잊으면 현재 구조에서는 복구할 수 없다.

### 3. MFA

비밀번호 외의 두 번째 인증 수단을 사용하지 않는다. 비밀번호가 노출될 경우 이를 보완하는 추가 인증 수단이 없다는 위험이 남아 있다.

### 4. PBKDF2 반복수의 런타임 제약

초기에는 더 높은 PBKDF2 반복수를 적용했지만 실제 Cloudflare Workers 배포 환경에서 가입 과정이 정상 동작하지 않아 현재는 100,000회로 조정했다. 현재 구현은 평문 저장을 피하고 계정별 salt를 적용하지만, 장기 운영 서비스라면 인증 전용 서비스나 더 강한 비밀번호 파생 방식을 안정적으로 지원하는 환경도 검토할 필요가 있다.

# 5일 실제 사용 기록

## 1일차에 고정한 기준

- 질문: `계획 규칙을 바꾸면 하루 ALEPT 과제 실제 집중 시간이 늘어나는가?`
- 관찰 지표: `ALEPT 과제 실제 집중 시간`
- 단위: `분`
- 최초 계획 규칙: `작업 시작 전에 오늘 할 일을 최대 3개만 정한다.`
- 계산 규칙: 각 날짜 입력값을 그대로 사용하고, 합계는 모든 기록값의 합, 평균은 합계를 기록 수로 나눈 값
- 빠진 값: 기록이 없으면 0으로 채우지 않고 미완성으로 둠
- 중복 값: 같은 KST 날짜의 두 번째 저장은 거절
- 튀는 값: 실제 값이면 임의 제외하지 않고 메모와 함께 보존
- 평균 반올림: 소수 1자리
- 주 시작 요일: 월요일

## 실제 기록

| 일차 | KST 날짜 | 값 | 적용 규칙 |
|---|---|---:|---|
| Day 1 | 2026-10-14 | 85분 | 최대 3개 |
| Day 2 | 2026-10-15 | 70분 | 최대 3개 |
| Day 3 | 2026-10-16 | 40분 | 최대 2개 |
| Day 4 | 2026-10-18 | 50분 | 최대 2개 |
| Day 5 | 2026-10-19 | 65분 | 최대 2개 |

Day 4 전날인 2026-10-17은 기록하지 못했으며, 임의로 소급 입력하거나 0으로 채우지 않았다.

## 계획 규칙 변경

- 위치: Day 2 기록 뒤 / Day 3 기록 앞
- 변경 시각: `2026-10-15 09:42:22 KST`
- 변경 전: `작업 시작 전에 오늘 할 일을 최대 3개만 정한다.`
- 변경 후: `작업 시작 전에 오늘 할 일을 최대 2개만 정한다.`
- 이유: 첫 2일 동안 최대 3개 규칙으로 진행한 결과와, 할 일 수를 2개로 줄였을 때 실제 집중 시간이 달라지는지 비교하기 위해 변경했다.

## 손으로 다시 계산

```text
합계 = 85 + 70 + 40 + 50 + 65
     = 310분

평균 = 310 ÷ 5
     = 62분
```

화면의 합계 `310분`, 평균 `62분`과 일치했다.

변경 전 평균:

```text
(85 + 70) ÷ 2 = 77.5분
```

변경 후 평균:

```text
(40 + 50 + 65) ÷ 3 = 51.7분(소수 1자리)
```

이번 5일 기록에서는 계획 규칙을 최대 3개에서 최대 2개로 줄인 뒤 실제 집중 시간이 늘지 않고 평균이 감소했다. 결과가 예상과 달라도 실제 기록을 그대로 보존했다.
