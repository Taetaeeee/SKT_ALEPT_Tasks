# T07 직접 검증 절차

이 문서는 **실제 배포 뒤 직접 확인할 순서**입니다. 제출물에는 실제 비밀번호·세션 쿠키·토큰을 복사하지 않습니다.

## 0. 시작 조건

- 원격 D1에 `0002_auth.sql` migration 적용
- 실제로 사용할 계정을 **첫 계정**으로 가입하여 T06 자료 승계
- 두 번째 검사 계정 B 생성
- 계정 A와 B 각각에 계획 1개, 할 일 1개 이상 준비
- 계정 A의 계획 ID/할 일 ID, 계정 B의 계획 ID/할 일 ID만 기록
- 비밀번호는 제출 문서에 기록하지 않음

## 1. 첫 화면 / 가입 / 로그인 / 로그아웃

1. 새 시크릿 창에서 결과물 주소를 연다.
2. 자료 대신 로그인 화면만 보이는지 확인한다.
3. 새 계정을 만든다.
4. 같은 아이디로 다시 가입해 `409 USERNAME_TAKEN`인지 확인한다.
5. 존재하는 아이디+틀린 비밀번호와 존재하지 않는 아이디로 각각 로그인한다.
6. 두 경우 모두 상태 401, 문구 `아이디 또는 비밀번호를 확인해 주세요.`가 같은지 확인한다.
7. 로그인 상태에서 `GET /api/plans` 성공 응답을 저장한다.
8. 로그아웃한다.
9. 같은 `GET /api/plans`를 다시 실행해 401 거절을 저장한다.

제출할 때 Cookie/Set-Cookie 값은 `pds_session=AbC…생략`처럼 가립니다.

## 2. 저장 비밀번호 / salt 확인

Cloudflare 터미널에서 다음처럼 **해시만** 확인합니다.

```bash
npx wrangler d1 execute t06-pds-diary-db --remote --command "SELECT id, username, password_hash FROM users ORDER BY id;"
```

확인할 것:

- 저장값이 `pbkdf2-sha256$100000$...` 형태인지
- 입력한 비밀번호 문자열이 저장값에 그대로 없는지
- 같은 비밀번호로 만든 두 검사 계정의 salt/derived key 부분이 서로 다른지

제출 문서에는 비밀번호를 절대 적지 않습니다.

## 3. 세션

로그인 뒤 Network에서 `GET /api/plans`의 Cookie를 볼 수 있지만 제출 캡처에서는 값 전체를 가립니다.

확인할 것:

- URL에 세션값이 없음
- 쿠키에 `HttpOnly`, `SameSite=Strict`, 배포 HTTPS에서는 `Secure`
- `/api/auth/me` 응답의 `session_expires_at`이 있음
- 로그아웃 뒤 이전 쿠키로 `/api/plans`가 401
- 비밀번호 변경 뒤 변경 전 세션이 더 이상 통하지 않음

## 4. 계정 A → 계정 B 자료 공격

브라우저 A에서 B의 ID를 알고 있다고 가정합니다. 개발자 도구 Console에서 실행하고 Network 응답을 저장합니다.

```js
// B 계획 읽기 시도
await fetch('/api/plans/<B_PLAN_ID>').then(async r => [r.status, await r.json()])

// B 계획 수정 시도: 소유권 검사에서 먼저 404가 나므로 빈 JSON이어도 됨
await fetch('/api/plans/<B_PLAN_ID>', {
  method: 'PUT', headers: {'content-type':'application/json'}, body: '{}'
}).then(async r => [r.status, await r.json()])

// B 할 일 삭제 시도
await fetch('/api/tasks/<B_TASK_ID>', {
  method: 'DELETE', headers: {'content-type':'application/json'}, body: '{}'
}).then(async r => [r.status, await r.json()])
```

세 요청 모두 404인지 확인합니다.

## 5. 계정 B → 계정 A 자료 공격

B로 로그인한 별도 창에서 위 세 요청을 A의 PLAN/TASK ID로 반복합니다. 역시 모두 404인지 확인합니다.

양방향 검사 전후로 각 계정에서 자기 자료를 다시 열어 건수와 내용이 그대로인지 확인합니다.

## 6. 목록 격리 + 주소/헤더/본문 위조

B 로그인 상태에서:

```js
// 주소(query)에 A user_id를 적어도 B 목록만 나와야 함
await fetch('/api/plans?user_id=<A_USER_ID>').then(r => r.json())

// 헤더에 A user_id를 적어도 B 목록만 나와야 함
await fetch('/api/plans', {headers: {'X-User-Id':'<A_USER_ID>'}}).then(r => r.json())
```

본문 위조는 B 소유 할 일을 수정할 때 임의 `user_id` 필드를 추가합니다. 서버는 그 필드를 무시하고 세션 B의 자기 할 일만 수정해야 합니다.

```js
await fetch('/api/tasks/<B_OWN_TASK_ID>', {
  method: 'PUT',
  headers: {'content-type':'application/json'},
  body: JSON.stringify({
    user_id: <A_USER_ID>,
    title: '본문 user_id 위조 검사',
    due_date: '2026-10-20',
    priority: 'medium',
    tag: 'security-test',
    estimated_minutes: 10
  })
}).then(async r => [r.status, await r.json()])
```

A 자료가 바뀌지 않고 B 자기 자료만 바뀌는지 확인합니다.

## 7. 로그인하지 않은 직접 API

로그아웃한 창에서:

```js
await fetch('/api/plans').then(async r => [r.status, await r.json()])
```

401 `UNAUTHORIZED`인지 확인합니다.

## 8. 5일 사용 기록

- 1일차: 질문/지표/단위/계획 규칙을 저장하고 오늘 값 1건 기록
- 같은 날 다시 저장 시도 → 409 `DUPLICATE_DATE`
- 2일차: 동일 지표로 1건 기록
- 2일차 뒤: 규칙 변경 폼에서 새 규칙/이유 기록
- 3~5일차: 같은 지표·단위로 계속 기록
- 5일 뒤: 기록이 정확히 5건인지 확인
- 합계는 5개 값을 직접 더함
- 평균은 합계 ÷ 5 후 설정한 자리로 반올림
- 화면 값과 직접 계산값이 일치하는지 기록

## 9. 내보내기 / 계정 삭제

- `내 자료 내보내기` 파일에 로그인 계정의 자료만 들어 있는지 확인
- `users.password_hash`, `sessions.token_hash`, 세션 쿠키 원문이 export에 없는지 확인
- 검사 계정에서 계정 삭제를 실행한 뒤 로그인할 수 없고 자료도 사라지는지 확인

## 10. 비밀값 검색

Git 저장소에서 다음 계열을 검색합니다.

```bash
git grep -nEi "password|token|secret|api[_-]?key|authorization"
```

코드의 변수명/필드명은 나올 수 있습니다. **실제 비밀번호·실제 세션값·실제 API 키/비밀키 원문이 커밋되어 있지 않은지** 확인합니다.
