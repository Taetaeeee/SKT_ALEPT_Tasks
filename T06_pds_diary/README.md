## 인증 구현 요약

- 인증 방식: 직접 구현 + Cloudflare Workers Web Crypto API
- 비밀번호: `PBKDF2-HMAC-SHA-256`, 100,000 iterations, 계정별 랜덤 salt
- 세션: 서버 저장형 opaque session
- 쿠키: `HttpOnly`, `SameSite=Strict`, `Secure`, 12시간 만료
- DB에는 세션 원문이 아니라 SHA-256 해시만 저장
- 로그아웃 시 현재 세션 폐기
- 비밀번호 변경 시 기존 세션 전체 폐기
- 계획·할 일·실행 기록·돌아보기는 서버에서 로그인 사용자의 소유권 검사
- 다른 사용자 자료 ID 요청은 404로 처리
- URL·헤더·본문에 임의 `user_id`를 보내도 인증 근거로 사용하지 않음
- 계정 삭제 시 해당 계정과 연결된 자료 삭제

## 실제 검증 결과

- 같은 아이디 재가입 거절 확인
- 존재하는 아이디 + 틀린 비밀번호 / 존재하지 않는 아이디의 로그인 실패 문구 동일 확인
- 비밀번호가 D1에 원문이 아닌 PBKDF2 해시로 저장됨 확인
- 같은 비밀번호를 사용한 두 계정의 저장 해시가 서로 다름 확인
- 로그인 상태 `GET /api/plans` → 200
- 로그아웃 뒤 같은 `GET /api/plans` → 401
- 비밀번호 변경 뒤 다른 브라우저의 기존 세션 → 401
- `test_a → test_b` 읽기·수정·삭제 → 모두 404
- `test_b → test_a` 읽기·수정·삭제 → 모두 404
- URL·헤더·본문 사용자 정보 위조 → 로그인한 계정의 자료만 반환
- 목록에 다른 계정 자료 0건 확인
- 공격 전후 상대 계정 자료 건수·내용 불변 확인
- 테스트 계정 삭제 뒤 사용자·계획·할 일 모두 0건 확인

## 짧은 확인 방법 4줄

1. **어디로 가나요:** https://t06-pds-diary.nalzzoaleph26.workers.dev/ 를 새 시크릿 창에서 엽니다.
2. **세 단계 안에 무엇을 하나요:** 로그인 화면 확인 → 직접 만든 계정으로 로그인 → PLAN/DO/SEE/5일 기록을 확인합니다.
3. **무엇이 보이면 통과인가요:** 로그인 뒤 내 자료만 보이고, 다른 계정 자료 ID 요청은 404, 로그아웃 뒤 같은 보호 API 요청은 401이면 통과입니다.
4. **안 될 때는 무엇이 보이나요:** 비로그인 보호 API는 `UNAUTHORIZED`, 남의 자료 ID는 `NOT_FOUND`, 같은 KST 날짜의 두 번째 5일 기록은 중복 저장이 거절됩니다.
